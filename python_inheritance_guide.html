Section 01

Single Inheritance

The simplest form: one child class inherits from exactly one parent. Python's super() call delegates to the parent's method through the MRO chain. Always call super().__init__() first — skipping it silently discards all parent-set attributes.

Review checklist
  • super().__init__() called in every child __init__
  • Method overrides intentionally replace parent behaviour
  • Parent attributes accessible on child instances
  • isinstance() returns True for parent and child
  • type() returns only the concrete class
  • __str__ / __repr__ use self.__class__.__name__
CRITICAL
The basic contract — parent, child, and super()
Why this matters
Single inheritance is the foundation of all OOP in Python. Getting super().__init__() wrong, or skipping it entirely, is the most common beginner mistake and silently breaks all parent-set attributes. Every other pattern in this guide builds on this contract. This pattern appears in nearly every Python class ever written. Mastering it eliminates an entire category of AttributeError bugs.
✗  Problematic code
class Animal:
    def __init__(self, name: str, age: int):
        self.name = name
        self.age  = age

    def breathe(self):
        return f"{self.name} breathes."


class Dog(Animal):
    def __init__(self, name: str, age: int, breed: str):
        # Missing super().__init__()!
        self.breed = breed

    def speak(self):
        return f"{self.name} says: Woof!"  # AttributeError!

    def breathe(self):
        # Overrides parent — but self.name doesn't exist
        return f"{self.name} pants."


dog = Dog("Rex", 5, "Lab")
print(dog.name)   # AttributeError: 'Dog' has no attribute 'name'
✓  Fixed code
class Animal:
    kingdom = "Animalia"   # class variable — shared

    def __init__(self, name: str, age: int):
        self.name = name          # instance variable
        self.age  = age

    def breathe(self):
        return f"{self.name} breathes."

    def __str__(self):
        return f"{self.__class__.__name__}(name={self.name})"


class Dog(Animal):
    def __init__(self, name: str, age: int, breed: str):
        super().__init__(name, age)  # ← ALWAYS first
        self.breed = breed

    def speak(self):
        return f"{self.name} says: Woof!"

    def breathe(self):              # intentional override
        return f"{self.name} pants and breathes."


dog = Dog("Rex", 5, "Labrador")
print(dog.name)              # Rex — parent attr present
print(dog.speak())           # Rex says: Woof!
print(isinstance(dog, Animal))  # True — chain check
print(type(dog) is Animal)   # False — exact type only
⚠ What is wrong
  • Missing super().__init__() — parent's self.name and self.age never set
  • Every method that touches self.name raises AttributeError at runtime
  • No error at class definition time — bug only surfaces when method is called
  • Overriding breathe() without parent state means the override can't use parent attrs
✔ Why the fix works
  • super().__init__(name, age) delegates to Animal's __init__ — all parent attrs created
  • Child then adds its own self.breed — both parent and child state coexist
  • isinstance(dog, Animal) is True — the whole chain is traversed
  • self.__class__.__name__ in __str__ prints the actual concrete class, not the defining class
Key Takeaways
  • Always call super().__init__() as the very first line in a child's __init__
  • Method overriding replaces the parent's version — use super().method() to extend it instead
  • Use isinstance(obj, ParentClass) for type checks — never type(obj) == ParentClass
  • Class variables (like kingdom) are shared across all instances — instance variables are per-object
Section 02

Multilevel Inheritance

A chain of three or more classes — A → B → C → D. Each level inherits all attributes and methods of every ancestor. Python's MRO ensures super() calls traverse the chain in order without calling any class twice.

Review checklist
  • Each level calls super().__init__() to propagate init chain
  • Chains deeper than 3 are a smell — consider composition instead
  • Grandparent methods accessible via normal attribute lookup
  • __mro__ attribute shows the full resolution order
MAJOR
Four-level chain — LivingThing → Vertebrate → Mammal → Whale
Why this matters
Each level in a multilevel chain must cooperatively call super().__init__(). If any level skips it, all ancestors above that point lose their initialisation — and no Python error is raised until you access a missing attribute.
python — multilevel_inheritance.py
Key Takeaways
  • Every level must call super().__init__() — one broken link silently drops all ancestors above it
  • Whale only calls super().__init__(lifespan=80) once — Python's MRO threads it through all 3 ancestors
  • All ancestor methods are available on the deepest child without any extra imports
  • Inspect ClassName.__mro__ to understand the full resolution order at any time
Section 03

Multiple Inheritance & MRO

One child inherits from two or more parents simultaneously. Python solves method conflicts with the C3 linearisation algorithm (MRO). The diamond problem — where a base class would otherwise be initialised twice — is eliminated by cooperative super() usage throughout the chain.

Review checklist
  • All parents use cooperative super(), not hardcoded parent names
  • MRO inspected with ClassName.__mro__ or help(ClassName)
  • Mixin base class order in the class definition matches intended priority
  • Diamond base initialised exactly once — confirmed by MRO
  • Conflicting method names in mixins resolved by MRO order, not magic
  • **kwargs forwarding used for compatible multi-parent __init__
CRITICAL
Diamond inheritance — Base called exactly once via cooperative super()
Why this matters
In a diamond hierarchy (Left and Right both inherit Base, Child inherits both), hardcoded Base.__init__(self) inside Left causes Base to be initialised twice — once from Left and once from Right. Cooperative super() guarantees every class in the chain is called exactly once, in MRO order. This is the single most misunderstood concept in Python OOP. Getting it wrong causes duplicate initialisation, duplicate side effects, and silent state corruption.
✗  Hardcoded calls — Base initialised twice
class Base:
    def __init__(self):
        print("Base.__init__")   # prints TWICE!
        self.value = 0

class Left(Base):
    def __init__(self):
        Base.__init__(self)   # hardcoded — bypasses MRO
        self.left = 1

class Right(Base):
    def __init__(self):
        Base.__init__(self)   # hardcoded — called again!
        self.right = 2

class Child(Left, Right):    # MRO: Child→Left→Right→Base
    def __init__(self):
        Left.__init__(self)
        Right.__init__(self)  # Base.__init__ fires again!

Child()
# Base.__init__   ← from Left
# Base.__init__   ← from Right (duplicate!)
✓  Cooperative super() — Base called once
class Base:
    def __init__(self):
        print("Base.__init__")   # prints ONCE
        super().__init__()
        self.value = 0

class Left(Base):
    def __init__(self):
        print("Left.__init__")
        super().__init__()   # MRO: next is Right, then Base
        self.left = 1

class Right(Base):
    def __init__(self):
        print("Right.__init__")
        super().__init__()   # MRO: next is Base
        self.right = 2

class Child(Left, Right):   # MRO: Child→Left→Right→Base
    def __init__(self):
        print("Child.__init__")
        super().__init__()  # threads through entire MRO

Child()
# Child.__init__
# Left.__init__
# Right.__init__  ← super() in Left called Right, not Base!
# Base.__init__   ← exactly once
⚠ What is wrong
  • Hardcoded Base.__init__(self) in Left and Right bypasses the MRO chain entirely
  • Base is initialised twice — any side effects (DB connection, file open) run twice
  • C class in the diamond (Right) is silently skipped if Left calls Base directly
  • Adding a new class to the hierarchy silently breaks all existing hardcoded calls
✔ Why the fix works
  • super() in each class calls the next in MRO, not the hardcoded parent
  • MRO for Child: Child → Left → Right → Base → object — every class called exactly once
  • Adding a new class anywhere only requires inserting it in the MRO — all super() calls adapt automatically
  • Python's C3 linearisation guarantees a consistent, conflict-free resolution order
Key Takeaways
  • Use super() everywhere in a multi-inheritance chain — never hardcode parent class names in __init__
  • In a diamond, super() in Left calls Right (not Base directly) — this is the whole point of MRO
  • Print ClassName.__mro__ to verify the resolution order before debugging
  • Mixin class order in class Child(A, B, C) determines which A/B/C method wins on conflict
Section 04

Abstract Base Classes

ABC + @abstractmethod enforce a contract: any concrete subclass must implement every abstract method, or Python raises TypeError at instantiation time — not at call time. This transforms runtime errors into class-definition errors.

Review checklist
  • All abstract methods implemented by every concrete subclass
  • ABC itself cannot be instantiated — confirmed with a test
  • Concrete methods in ABC provide shared logic all children use
  • @abstractmethod used instead of raise NotImplementedError
  • @abstractclassmethod / @abstractstaticmethod for class/static contracts
  • isinstance(obj, ABCName) works for checking protocol compliance
CRITICAL
raise NotImplementedError vs @abstractmethod — enforcement timing
Why this matters
Using raise NotImplementedError in a base method only fails at call time. An object can be created, passed around, and stored — only failing when the method is actually invoked. @abstractmethod fails at instantiation time, immediately — turning a runtime surprise into a class-definition guarantee.
✗  raise NotImplementedError — too late
class Shape:
    def area(self) -> float:
        raise NotImplementedError("subclasses must implement")
    def perimeter(self) -> float:
        raise NotImplementedError("subclasses must implement")

class BrokenCircle(Shape):
    pass  # forgot to implement area() and perimeter()

# No error here — object created successfully!
c = BrokenCircle()
# Error only surfaces here, much later:
c.area()  # NotImplementedError: subclasses must implement
✓  @abstractmethod — fails at class instantiation
import math
from abc import ABC, abstractmethod

class Shape(ABC):
    def __init__(self, color: str = "white"):
        self.color = color

    @abstractmethod
    def area(self) -> float: ...

    @abstractmethod
    def perimeter(self) -> float: ...

    # Concrete method — shared by ALL subclasses for free
    def describe(self) -> str:
        return (f"{type(self).__name__} | color={self.color} | "
                f"area={self.area():.2f} | perim={self.perimeter():.2f}")

class Circle(Shape):
    def __init__(self, r: float, color: str = "white"):
        super().__init__(color); self.r = r
    def area(self): return math.pi * self.r ** 2
    def perimeter(self): return 2 * math.pi * self.r

# TypeError immediately — can't miss it:
Shape()  # TypeError: Can't instantiate abstract class Shape
Circle(5, "red").describe()  # works perfectly
⚠ What is wrong
  • Object created successfully even when required methods are missing
  • Error only fires when the missing method is actually called — potentially in production
  • No way to enforce the contract at class definition or test time
  • Forgetting one method in a large subclass is easy — silent until invoked
✔ Why the fix works
  • TypeError raised at Shape() or any subclass that doesn't implement both methods
  • Concrete methods in ABC (like describe()) are inherited for free by all subclasses
  • @abstractmethod + ... body is idiomatic — the ... serves as the docstring placeholder
  • isinstance(Circle(5), Shape) → True — ABC registers the type relationship
Key Takeaways
  • Always use ABC + @abstractmethod instead of raise NotImplementedError for interface contracts
  • ABCs can have concrete methods — useful for shared logic that all subclasses need
  • @staticmethod @abstractmethod (stack both decorators) enforces static method contracts
  • Run issubclass(MyClass, Shape) in tests to verify your class hierarchy is correctly structured
Section 05

Mixin Classes

Mixins provide reusable, optional behaviour without being standalone parents. They are designed to be combined with other classes, not instantiated directly. The order of mixins in the class definition determines which mixin's method wins in a conflict.

Review checklist
  • Mixin names end in Mixin by convention (SerializeMixin, LogMixin)
  • Mixins don't call super().__init__() unless they add state
  • Mixin order in the class list determines priority: leftmost wins
  • No circular dependency between mixin and the class using it
  • Multiple mixins on one class are fine — they stack cleanly via MRO
  • Mixin methods only use attributes the target class is expected to have
MAJOR
Mixin ordering changes behaviour — leftmost wins on conflict
Why this matters
When two mixins define the same method name, the one listed first in the class definition wins. This is not random — it is determined by Python's MRO. Developers who swap mixin order expecting the same result will get silently different behaviour.
✗  Mixin order not considered
class JSONSave:
    def save(self): return "Saving as JSON"

class DBSave:
    def save(self): return "Saving to Database"

# Developer swaps order thinking it doesn't matter:
class Report(DBSave, JSONSave):  # DBSave first
    pass

class Archive(JSONSave, DBSave): # JSONSave first
    pass

print(Report().save())   # "Saving to Database"
print(Archive().save())  # "Saving as JSON"
# Same two mixins, different result — easy to miss in review
✓  Intentional ordering with explicit override
class SerializeMixin:
    # Provides JSON serialisation to any class.
    def to_dict(self) -> dict: return self.__dict__
    def to_json(self) -> str:
        import json; return json.dumps(self.to_dict(), indent=2)

class LogMixin:
    # Provides logging to any class.
    _log: list = []
    def log(self, msg: str):
        entry = f"[{type(self).__name__}] {msg}"
        self._log.append(entry); print(entry)

class Employee(SerializeMixin, LogMixin):
    # Explicitly ordered: serialise takes precedence.
    def __init__(self, id: int, name: str, salary: float):
        self.id = id; self.name = name; self.salary = salary
    def give_raise(self, pct: float):
        self.salary *= (1 + pct / 100)
        self.log(f"Raise {pct}%. New salary: {self.salary:.2f}")

e = Employee(1, "Alice", 60_000)
e.give_raise(10)
print(e.to_json())  # serialises all fields
⚠ What is wrong
  • Swapping mixin order silently changes which save() is called — no error or warning
  • Code review may not catch this — both orderings are syntactically valid
  • When mixins have different __init__ signatures, wrong order causes wrong args being passed
✔ Why the fix works
  • Each mixin has a clear, single responsibility — no conflicting method names
  • When conflict is unavoidable, document the intended order explicitly in the class docstring
  • Inspecting Employee.__mro__ shows exactly which class wins for each method
Key Takeaways
  • Mixin order in class Child(MixinA, MixinB, Base) is intentional — leftmost takes precedence
  • Name mixins with the Mixin suffix so readers know they're not standalone classes
  • Keep mixins stateless where possible — mixins that add state make cooperative __init__ required
  • Test mixin combinations explicitly — MRO surprises only appear when method names collide

Tricky Examples

22 non-obvious inheritance behaviours that surprise even experienced Python developers. Each example is a minimal, runnable demonstration with explanation.

TRICKY 1
Class variable mutation trap — shared list across all instances
Why this matters
A mutable class variable (list, dict) is shared across ALL instances. Calling self.items.append(x) mutates the class-level object — it does NOT create a per-instance list. This is one of the most common beginner Python bugs.
✗  Shared mutable class variable
class SharedList:
    items = []   # shared across ALL instances!

    def add(self, item):
        self.items.append(item)  # mutates class-level list

a = SharedList(); b = SharedList()
a.add("x"); b.add("y")
print(a.items)   # ['x', 'y']  ← WRONG: b's item is here!
print(b.items)   # ['x', 'y']  ← same object!
✓  Instance variable in __init__
class SafeList:
    def __init__(self):
        self.items = []   # new list per instance

    def add(self, item):
        self.items.append(item)

c = SafeList(); d = SafeList()
c.add("x"); d.add("y")
print(c.items)   # ['x']  ← correct: independent
print(d.items)   # ['y']  ← independent
Key Takeaways
  • Class variables are shared — only use them for constants or counters you want shared (like _count)
  • Mutable defaults (list, dict, set) must always be created in __init__ as instance variables
  • This applies equally to function default arguments: def f(x, items=[]) is the same bug
TRICKY 2
super() follows MRO, not the named parent — the cooperative chain surprise
Why this matters
In a diamond hierarchy, super() inside B2 does NOT call A2 directly — it calls the next class in the MRO of the final class, which is C2. This is counterintuitive until you understand that super() is about MRO position, not parent relationship.
python — super_mro_surprise.py 
class A2:
    def hello(self):
        print("A2.hello")

class B2(A2):
    def hello(self):
        print("B2.hello")
        super().hello()  # Does NOT call A2 directly!
                         # Calls whatever is next in D2's MRO

class C2(A2):
    def hello(self):
        print("C2.hello")
        super().hello()

class D2(B2, C2):
    def hello(self):
        print("D2.hello")
        super().hello()

# MRO: D2 → B2 → C2 → A2
D2().hello()
# D2.hello
# B2.hello
# C2.hello   ← super() in B2 called C2, NOT A2!
# A2.hello

print([c.__name__ for c in D2.__mro__])
# ['D2', 'B2', 'C2', 'A2', 'object']
Key Takeaways
  • super() means "next in the MRO of the actual concrete class", not "my declared parent"
  • This is why cooperative super() works — every class in the chain gets called exactly once
  • Always inspect D2.__mro__ when debugging unexpected super() call order
TRICKY 3
Inheriting from built-in types — list, dict, int
Why this matters
Python built-in types are fully subclassable. You can create a list that caps its size, a dict that auto-lowercases keys, or an int with extra methods — without wrapping or composition.
python — builtin_subclassing.py 
class CappedList(list):
    # A list that silently ignores appends beyond max size.
    def __init__(self, max_size: int):
        super().__init__()
        self.max_size = max_size

    def append(self, item):
        if len(self) < self.max_size:
            super().append(item)   # delegate to list.append
        else:
            print(f"  CappedList full ({self.max_size}), ignoring {item!r}")

cl = CappedList(3)
for i in range(5): cl.append(i)
print(cl)  # [0, 1, 2]


class LowerDict(dict):
    # A dict that lower-cases all string keys automatically.
    def __setitem__(self, key, value):
        super().__setitem__(key.lower() if isinstance(key, str) else key, value)

    def __getitem__(self, key):
        return super().__getitem__(key.lower() if isinstance(key, str) else key)

ld = LowerDict()
ld["Name"] = "Alice"; ld["AGE"] = 30
print(dict(ld))    # {'name': 'Alice', 'age': 30}
print(ld["NAME"])  # Alice
Key Takeaways
  • Subclassing builtins is idiomatic Python — use super().method() to delegate to the original implementation
  • Override only the specific dunder you need — all other list/dict behaviour is inherited for free
  • Note: UserList and UserDict in collections are easier to subclass safely if you need full override control

Bug Analyses

21 real inheritance bugs — each shown as wrong code, explained in detail, then fixed. These are the patterns that silently pass tests but break in production.

BUG 3
Class variable shadowed by instance variable — silent inconsistency
Why this matters
Writing self.count += 1 reads the class variable, then creates a new instance variable to store the result. The class variable is never updated. This is one of the most confusing Python attribute lookup behaviours.
✗  self.count += 1 creates instance shadow
class Counter:
    count = 0   # class variable

    def __init__(self):
        self.count += 1  # WRONG: reads class, writes instance!
        #  self.count = self.count + 1
        #  read: class var (0)
        #  write: new instance var!

c1 = Counter(); c2 = Counter()
print(c1.count)        # 1 (instance var)
print(c2.count)        # 1 (instance var)
print(Counter.count)   # 0 — class var NEVER updated!
✓  Use ClassName.var to update class variable
class Counter:
    count = 0

    def __init__(self):
        Counter.count += 1  # modifies class variable directly

c1 = Counter(); c2 = Counter()
print(c1.count)        # 2 (inherited from class)
print(c2.count)        # 2 (inherited from class)
print(Counter.count)   # 2 — correctly updated!

# Alternative: use cls in a classmethod
class Counter2:
    count = 0
    def __init__(self): type(self).count += 1  # subclass-safe
⚠ What is wrong
  • self.count += 1 expands to self.count = self.count + 1 — the write creates an instance attr
  • Class variable stays at 0 forever — the "global" counter is broken
  • c1 and c2 each have their own count = 1 — the class var is shadowed but never shared
✔ Why the fix works
  • Counter.count += 1 directly modifies the class-level attribute — no instance shadow created
  • type(self).count += 1 is subclass-safe — updates the actual class of the instance, not the hardcoded parent
  • All instances see the updated class variable because none of them shadow it with an instance attr
Key Takeaways
  • To update a class variable, use ClassName.var or type(self).var — never self.var
  • Attribute lookup order: instance __dict__ → class __dict__ → parent classes
  • Writing via self.var = ... always creates or updates the instance attribute, never the class attribute
BUG 12
Diamond problem without cooperative super() — Base.__init__ called twice
Why this matters
Hardcoding parent class names in __init__ in a diamond hierarchy causes the shared base class to be initialised twice. Any resource opened in the base (DB connection, file handle, counter increment) runs twice — silently corrupting state.
✗  Hardcoded calls — Base.__init__ twice
class Base:
    def __init__(self):
        print("Base.__init__")  # prints TWICE
        self.value = 0

class Left(Base):
    def __init__(self):
        Base.__init__(self)  # hardcoded
        self.left = 1

class Right(Base):
    def __init__(self):
        Base.__init__(self)  # hardcoded — fires again!
        self.right = 2

class Both(Left, Right):
    def __init__(self):
        Left.__init__(self)
        Right.__init__(self)  # Base runs again here!

Both()  # Base.__init__ printed TWICE
✓  Cooperative super() — Base.__init__ once
class Base:
    def __init__(self):
        print("Base.__init__")  # prints ONCE
        super().__init__()
        self.value = 0

class Left(Base):
    def __init__(self):
        super().__init__()  # MRO-aware
        self.left = 1

class Right(Base):
    def __init__(self):
        super().__init__()  # MRO-aware
        self.right = 2

class Both(Left, Right):
    def __init__(self):
        super().__init__()  # threads through MRO

Both()  # Base.__init__ printed exactly ONCE
# MRO: Both → Left → Right → Base
Key Takeaways
  • In any diamond hierarchy, all classes must use cooperative super() — one hardcoded call breaks the whole chain
  • If the base opens a DB connection, file, or increments a counter — it runs twice with hardcoded calls
  • Test: print a message in Base.__init__ and count how many times it appears in the output
Real-world impact A payment service with hardcoded parent calls in a diamond initialised a DB connection pool twice. Under load, this doubled the connection count, exhausting the pool limit and causing intermittent connection timeouts that took 3 hours to diagnose.
Section 07

Static Concepts

@staticmethod has no implicit first argument — it's just a namespaced function. @classmethod receives cls — the actual class it is called on, not the class that defined it. This distinction is critical for factory methods and class-level registries.

Review checklist
  • @staticmethod used for pure utility — no self or cls needed
  • @classmethod used when the method needs the class (factory, registry)
  • cls in @classmethod is the subclass when called on a subclass
  • Class variables accessed via cls.var inside classmethods
  • Static/class methods inherited without needing to re-declare
  • Abstract static methods use stacked @staticmethod @abstractmethod
CRITICAL
@classmethod cls is the subclass — the factory pattern key
Why this matters
When a @classmethod uses cls() to create an instance, and is called on a subclass, it creates an instance of the subclass — not the class that defined the method. This is the foundation of the factory pattern in Python. A hardcoded ParentClass() would break this.
✗  Hardcoded class name — subclass gets wrong type
class Colour:
    def __init__(self, r, g, b):
        self.r, self.g, self.b = r, g, b

    @classmethod
    def from_hex(cls, hex_str: str):
        hex_str = hex_str.lstrip("#")
        r = int(hex_str[0:2], 16)
        g = int(hex_str[2:4], 16)
        b = int(hex_str[4:6], 16)
        return Colour(r, g, b)  # WRONG: hardcoded Colour!

class NamedColour(Colour):
    def __init__(self, r, g, b, name=""):
        super().__init__(r, g, b); self.name = name

c = NamedColour.from_hex("#FF5733")
print(type(c))   #  — WRONG!
                  # Should be NamedColour
✓  Use cls() — returns the actual subclass
class Colour:
    def __init__(self, r, g, b):
        self.r, self.g, self.b = r, g, b

    @classmethod
    def from_hex(cls, hex_str: str):
        hex_str = hex_str.lstrip("#")
        r = int(hex_str[0:2], 16)
        g = int(hex_str[2:4], 16)
        b = int(hex_str[4:6], 16)
        return cls(r, g, b)    # cls = whatever class called this

    @classmethod
    def from_tuple(cls, t: tuple):
        return cls(*t)         # works for subclasses too

class NamedColour(Colour):
    def __init__(self, r, g, b, name=""):
        super().__init__(r, g, b); self.name = name

c1 = Colour.from_hex("#FF5733")
print(type(c1))  # 

c2 = NamedColour.from_hex("#1E90FF")
print(type(c2))  #  ← correct!
⚠ What is wrong
  • Hardcoded Colour(r, g, b) always creates a Colour — even when called on NamedColour
  • Subclass-specific attributes (like name) are silently lost
  • Any further subclassing produces the wrong type from all factory methods
✔ Why the fix works
  • cls is the class the method is called on — NamedColour when called on NamedColour
  • cls(r, g, b) calls NamedColour.__init__ — the right constructor for the right class
  • This pattern is used in Python's stdlib: datetime.fromisoformat(), int.from_bytes()
Key Takeaways
  • In @classmethod factories, always use cls() not ClassName() — it's the whole point of receiving cls
  • @staticmethod has no cls or self — it cannot be a factory for subclasses
  • Use @classmethod for: alternate constructors, registries, subclass-aware configuration
  • Use @staticmethod for: pure utility functions logically grouped with the class
Section 10

Exception Handling

Exception handling in Python has nuances that catch even experienced developers: bare except: swallows keyboard interrupts, re-raising incorrectly loses tracebacks, and finally with a return silently overrides the try result.

Review checklist
  • Specific exceptions caught — never bare except:
  • Exception chaining preserved with raise ... from e
  • No return in finally — overrides try/except result silently
  • Custom exception hierarchy rooted at a domain base class
  • KeyboardInterrupt/SystemExit never caught by except Exception
  • Context managers preferred over try/finally for resource cleanup
CRITICAL
Bare except: catches KeyboardInterrupt — program can never quit
Why this matters
A bare except: (with no exception class) catches everything including KeyboardInterrupt (Ctrl+C) and SystemExit. This can make a program impossible to stop from the terminal, and hides completely unrelated bugs like NameError and TypeError.
✗  Bare except — swallows everything
def process(data):
    try:
        result = transform(data)
        return result
    except:           # catches EVERYTHING
        pass          # silently swallows bugs!

# KeyboardInterrupt (Ctrl+C) — swallowed!
# SystemExit (sys.exit()) — swallowed!
# NameError from a typo — swallowed!
# Your actual bug — hidden!

while True:
    process(get_data())  # can never be stopped
✓  Catch only what you expect
def process(data):
    try:
        result = transform(data)
        return result
    except ValueError as e:       # only what transform raises
        logger.warning("Bad data: %s", e)
        return None
    except (IOError, OSError) as e:
        logger.error("IO failure: %s", e)
        raise                      # re-raise — caller handles

# KeyboardInterrupt propagates naturally — Ctrl+C works
# SystemExit propagates — sys.exit() works
# NameError propagates — bug is visible in logs
# ValueError handled — expected condition managed
⚠ What is wrong
  • Bare except: catches BaseException — includes KeyboardInterrupt and SystemExit
  • Program cannot be interrupted with Ctrl+C — appears frozen to the user
  • Real bugs (NameError, AttributeError) are silently swallowed — never appear in logs
  • Catching everything is always wrong — you can't handle what you can't predict
✔ Why the fix works
  • except ValueError catches only what transform() is documented to raise
  • KeyboardInterrupt and SystemExit inherit from BaseException, not Exception — they bypass all except Exception clauses
  • Bare raise re-raises the original exception with its full traceback intact
Key Takeaways
  • Never use bare except: — always name the exception: except ValueError
  • except Exception is the widest acceptable catch — it still lets KeyboardInterrupt and SystemExit through
  • Bare raise inside an except block re-raises with the original traceback — use it for logging-then-reraise
  • Custom exception hierarchies: AppError → NetworkError → TimeoutError — catch at the right level
MAJOR
return in finally silently overrides the try/except result
Why this matters
A return statement inside a finally block overrides whatever value was being returned from the try or except block. This is one of Python's most surprising behaviours and can hide exceptions entirely.
✗  return in finally — overrides try result
def tricky():
    try:
        return "from try"
    finally:
        return "from finally"  # overrides try return!

print(tricky())  # "from finally" — surprising!

def even_worse():
    try:
        raise ValueError("important error")
    finally:
        return "ok"  # exception SWALLOWED silently!

print(even_worse())  # "ok" — ValueError disappeared!
✓  No return in finally — use for cleanup only
def safe():
    result = None
    try:
        result = compute()       # set result in try
    except ValueError as e:
        result = default_value   # handle in except
        logger.error("Error: %s", e)
    finally:
        cleanup()                # cleanup ONLY — no return!
    return result                # return AFTER try/finally

def safe_resource():
    resource = acquire()
    try:
        return process(resource)
    finally:
        resource.release()      # always releases — no return
Key Takeaways
  • Never put return in a finally block — it overrides any exception or return value from try/except
  • finally is for cleanup only: closing files, releasing locks, disconnecting from resources
  • Place the return statement after the entire try/except/finally block, not inside it
  • Prefer context managers (with) over try/finally for resource management — they're cleaner and safer
Section 11

Advanced Patterns

Descriptors, metaclasses, __slots__, __init_subclass__, and __new__ — the deeper Python OOP machinery used for frameworks, ORMs, and validation libraries.

Review checklist
  • __slots__ declared in every class in the chain for full memory savings
  • Descriptors use __set_name__ to receive the attribute name automatically
  • Metaclasses used only when class decorators or __init_subclass__ won't suffice
  • __new__ used for immutable types, caching, and singleton patterns
  • __init_subclass__ used for plugin registration and subclass validation
  • Singleton metaclass — _instances dict keyed on cls, not hardcoded class
MAJOR
__slots__ in parent but not child — memory savings silently lost
Why this matters
If a parent class defines __slots__ but a child class does not, Python adds __dict__ back to the child. This silently re-enables arbitrary attribute assignment and eliminates the memory savings that __slots__ was supposed to provide.
✗  __slots__ missing in child — __dict__ reappears
class Base:
    __slots__ = ("x", "y")   # memory-efficient
    def __init__(self, x, y): self.x, self.y = x, y

class Child(Base):
    # No __slots__ defined!
    # Python adds __dict__ to Child automatically
    pass

c = Child(1, 2)
c.x = 10             # still works (from slot)
c.unexpected = "oops" # works! __dict__ is back
print(hasattr(c, "__dict__"))  # True — slots failed!
✓  __slots__ in every class in the chain
class Base:
    __slots__ = ("x", "y")
    def __init__(self, x, y): self.x, self.y = x, y

class Child(Base):
    __slots__ = ("z",)       # adds z; inherits x, y from Base
    def __init__(self, x, y, z):
        super().__init__(x, y)
        self.z = z
    def volume(self): return self.x * self.y * self.z

c = Child(3, 4, 5)
print(c.volume())    # 60
try:
    c.unexpected = "oops"
except AttributeError as e:
    print(f"Blocked correctly: {e}")
print(hasattr(c, "__dict__"))  # False — slots intact
Key Takeaways
  • For __slots__ to work in a hierarchy, every class must define __slots__
  • Child's __slots__ only needs to list new attributes — parent slots are inherited automatically
  • __slots__ saves ~50 bytes per instance — critical when storing millions of objects
  • Use @dataclass(slots=True) in Python 3.10+ for slot efficiency with dataclass ergonomics
Section 12

File Operations with Inheritance

File operation classes demonstrate how inheritance, mixins, context managers, and exception handling combine in real systems. A FileManager base provides all I/O primitives; specialised subclasses inherit them and add domain logic.

Review checklist
  • Context managers used for all file I/O — never manual open/close
  • Encoding always specified explicitly — never rely on platform default
  • Binary files opened with "rb"/"wb" modes
  • CSV opened with newline="" to prevent double-newline on Windows
  • Pickle never used on untrusted external data (RCE risk)
  • Temp directories cleaned up with tempfile.TemporaryDirectory context manager
MAJOR
FileManager hierarchy — base I/O + specialised subclasses
python — file_manager_hierarchy.py 
import os, json, csv, tempfile
from abc import ABC, abstractmethod

class FileManager:
    # Base: all file I/O primitives inherited by subclasses.

    @staticmethod
    def write_text(path: str, content: str, mode: str = "w",
                   encoding: str = "utf-8"):
        with open(path, mode, encoding=encoding) as fh:
            fh.write(content)

    @staticmethod
    def read_text(path: str, encoding: str = "utf-8") -> str:
        with open(path, "r", encoding=encoding) as fh:
            return fh.read()

    @staticmethod
    def write_json(path: str, obj, indent: int = 2):
        with open(path, "w", encoding="utf-8") as fh:
            json.dump(obj, fh, indent=indent)

    @staticmethod
    def read_json(path: str):
        with open(path, "r", encoding="utf-8") as fh:
            return json.load(fh)

    @staticmethod
    def write_csv(path: str, rows: list, header: list = None):
        with open(path, "w", newline="", encoding="utf-8") as fh:
            writer = csv.writer(fh)
            if header: writer.writerow(header)
            writer.writerows(rows)

    @staticmethod
    def ensure_dir(path: str):
        os.makedirs(path, exist_ok=True)


class EmployeeFileManager(FileManager):
    # Inherits all FileManager I/O - adds employee domain logic.

    def save_employee(self, emp_dict: dict, directory: str) -> str:
        self.ensure_dir(directory)
        path = os.path.join(directory, f"emp_{emp_dict['id']}.json")
        self.write_json(path, emp_dict)
        return path

    def export_csv(self, employees: list, path: str):
        header = ["id", "name", "salary"]
        rows = [[e["id"], e["name"], f"{e['salary']:.2f}"]
                for e in employees]
        self.write_csv(path, rows, header=header)


class BaseFileProcessor(ABC, FileManager):
    # Abstract base: subclasses process specific file types.
    def __init__(self, path: str):
        self.path = path
        if not os.path.exists(path):
            raise FileNotFoundError(f"File not found: {path}")

    @abstractmethod
    def process(self) -> dict: ...

    def safe_process(self) -> dict:
        try:
            return self.process()
        except json.JSONDecodeError as e:
            raise ValueError(f"Corrupt file {self.path}: {e}") from e


class JSONProcessor(BaseFileProcessor):
    def process(self) -> dict:
        return self.read_json(self.path)

class TextProcessor(BaseFileProcessor):
    def process(self) -> dict:
        lines = self.read_text(self.path).splitlines()
        return {"lines": len(lines),
                "words": sum(len(l.split()) for l in lines)}


# Demo
with tempfile.TemporaryDirectory() as d:
    # Save some JSON
    efm = EmployeeFileManager()
    p = efm.save_employee({"id": 1, "name": "Alice", "salary": 75000}, d)

    # Process it back
    jp = JSONProcessor(p)
    print(jp.safe_process())   # {'id': 1, 'name': 'Alice', ...}

    # Text file
    tp_path = os.path.join(d, "notes.txt")
    FileManager.write_text(tp_path, "Python is powerful.\nInheritance is elegant.\n")
    tp = TextProcessor(tp_path)
    print(tp.safe_process())   # {'lines': 2, 'words': 6}
Key Takeaways
  • Static methods on a base class are the cleanest way to share pure utilities — no instance state needed
  • Combining ABC with FileManager via multiple inheritance gives each processor both the contract and the tools
  • Always specify encoding="utf-8" — platform default encoding varies across OS and Python version
  • Use tempfile.TemporaryDirectory() as context manager — cleanup is guaranteed even on exception
