Caching

Caching stores frequently accessed data in fast memory to reduce latency and database load. It's the #1 technique for scaling read-heavy systems.

▲ Cache Strategies: Cache-Aside vs Write-Through vs Write-Back — flow, pros/cons, and use cases
StrategyHow It WorksBest ForRisk
Cache-Aside (Lazy)App checks cache → miss → load DB → write to cacheRead-heavy; data not always needed3-op miss penalty; stale on write
Write-ThroughWrite to cache AND DB simultaneouslyRead-heavy; consistency criticalWrite latency doubled; wasted cache space
Write-BackWrite only to cache; async flush to DB laterWrite-heavy (gaming, logs)Data loss if cache crashes before flush
Read-ThroughCache auto-loads from DB on miss transparentlySimpler app codeCold cache = all misses initially
Refresh-AheadProactively refresh cache before TTL expiresPredictable access patternsMay cache data that won't be read

Eviction Policies

PolicyLogicUse Case
LRU (Least Recently Used)Evict item not accessed the longestGeneral purpose — most common
LFU (Least Frequently Used)Evict item accessed fewest timesPopularity-based content (news, trending)
TTL (Time-To-Live)Expire item after fixed time windowSession tokens, rate limits, OTPs
FIFOEvict oldest inserted itemSimple queues, log rotation
MRUEvict most recently used itemScan-resistant; prevents batch from thrashing

Cache Stampede — Problem & Solutions

▲ Cache Stampede: Simultaneous cache misses overwhelm DB — 4 solutions side by side
⚡
Cache Stampede / Thundering Herd
Problem: Popular item TTL expires → 10,000 requests simultaneously hit DB

Solutions

  • Mutex/Lock: First request acquires Redis SETNX lock. Others wait or return stale. Only one DB call.
  • TTL Jitter: TTL = base_ttl ± random(0–30s). Keys expire at different times, spreading load.
  • Probabilistic Early Expiry: As TTL approaches 0, random chance to refresh increases. Hot keys refresh before expiring.
  • Stale-While-Revalidate: Serve stale data immediately; refresh in background async thread.
  • Refresh-Ahead: Dedicated worker refreshes all hot keys every N seconds based on access frequency.
🔥
Cache Poisoning / Stale After Update
Problem: DB updated but cache still holds old data — users see wrong prices or inventory

Solutions

  • Write-Through: Always update cache synchronously with every DB write.
  • Explicit Invalidation: On any DB write (via ORM hooks), delete the affected cache key immediately.
  • CDC (Change Data Capture): Use Debezium to stream DB row changes → Kafka → invalidation consumer clears cache.
  • Versioned Keys: cache key = order:123:v5. Increment version on update → new URL = instant invalidation.
  • Short TTL as Safety Net: Even without explicit invalidation, data auto-refreshes at TTL expiry.

Redis vs Memcached

✅ Use Redis When

  • Data structures (sorted sets, lists, hashes)
  • Persistence (AOF/RDB snapshots)
  • Pub/Sub messaging or distributed locks
  • Geospatial queries (GEORADIUS)
  • Lua scripting for atomic operations
  • Cluster mode for horizontal scaling

✅ Use Memcached When

  • Pure key-value, simple string values
  • Multi-threaded performance on multi-core
  • Very large datasets, horizontal scale
  • No persistence required
  • Simpler operational management
⚠️ Cache Key Design Best Practices

Use hierarchical keys: service:entity:id:field (e.g. orders:restaurant:42:pending). Add version suffix for schema changes. Keep keys short — stored in memory. Document all patterns in a schema registry. Namespace per environment: prod:user:123.

Kafka & Message Queues

Message queues and event streaming platforms decouple producers from consumers, enable async processing, provide durability, and gracefully buffer traffic spikes.

▲ Kafka Architecture: topics partitioned across brokers, multiple independent consumer groups reading the same events
★ Key Insight: Consumer Groups

Each consumer group gets its own read cursor (offset) on every partition. kitchen-service and analytics-service both consume the same 'orders' topic independently. Analytics processing never slows down kitchen delivery. Add a new consumer group any time without affecting existing consumers.

Delivery Semantics

▲ Kafka Delivery Semantics: At-most-once, at-least-once, exactly-once — guarantees, config, and when to use each
SemanticGuaranteeProducer ConfigConsumer ConfigUse Case
At-Most-Once0 or 1 deliveryacks=0Auto-commit before processingMetrics, non-critical logs
At-Least-Once1+ deliveries (duplicates possible)acks=allManual commit after processingMost systems — add idempotency
Exactly-OncePrecisely 1 deliveryenable.idempotence=true + transactional.idread_committed + transactional outboxPayments, financial events
💡 How to Achieve Exactly-Once (Interview Answer)

Three layers: (1) Idempotent producer: enable.idempotence=true — Kafka deduplicates retries on broker. (2) Transactions: set transactional.id, use beginTransaction()/commitTransaction(). (3) Transactional consumer: write result + commit offset in the SAME database transaction (Outbox pattern). Note: exactly-once is within Kafka. For external sinks (DBs, APIs), you still need idempotency keys.

Scenarios — Simple to Complex

📦
Simple: Order Event Fan-Out
Problem: Order placed — kitchen, notifications, and analytics all need to react

Solutions

  • Partition key = restaurant_id → all orders for restaurant #42 → same partition → sequential ordering guaranteed.
  • Kitchen service processes one partition → no race conditions on order state machine within a restaurant.
  • Analytics reads same events independently → heavy analytics queries never affect real-time kitchen flow.
  • Each consumer group has its own offset — add new consumers (fraud detection, CRM) without touching existing ones.
⚡
Driver Not Notified When Order is Ready
Problem: Restaurant marks order ready but driver's app doesn't receive the push notification

Solutions

  • Consumer lag monitoring: alert if consumer group lag on 'order-ready' topic > 100 messages. Fix: add more consumer instances.
  • Push notification failure: Failed pushes go to notifications.DLT (Dead Letter Topic). Separate DLQ worker retries or alerts.
  • ACK pattern: Driver app ACKs notification via POST /ack. No ACK in 15s → retry push. Still no ACK → SMS fallback via Twilio.
  • Fallback chain: Push (attempt 1) → 15s → retry push (attempt 2) → 15s → SMS → in-app polling if all fail.
  • Idempotency: notification_id as idempotency key on driver side → retries never deliver duplicate notifications.
  • State machine: ORDER_READY → NOTIFYING_DRIVER → DRIVER_NOTIFIED → DRIVER_EN_ROUTE. Stuck >60s → PagerDuty alert.
🔄
Complex: Multi-Service Saga with Compensation
Problem: Place order → Reserve inventory → Charge payment → Create shipment. Any step can fail.

Solutions

  • Orchestration Saga: Central saga orchestrator sends commands and awaits replies. Manages explicit state machine. Easier to monitor than choreography.
  • Compensation: If 'Charge Payment' fails → emit 'ReleaseInventory' command → emit 'CancelOrder' command. Each compensating action is idempotent.
  • Transactional Outbox: Each service writes business data + event in same local DB transaction. Relay process publishes to Kafka. Eliminates dual-write inconsistency.
  • Idempotent consumers: Every service checks if saga_id already processed. Safe to replay on failure.
  • Saga timeout: Each step has a deadline (e.g., 30s). If 'reserve-inventory' hasn't responded → treat as failure → compensate.

Hot Partition Problem

⚠️ Hot Partition Problem

If restaurant_id is partition key and McDonald's gets 100× more orders than a local cafe, its partition is overwhelmed while others are idle.
Fix 1: Composite key = restaurant_id + random_suffix(0–9) — spreads load across 10 partitions but sacrifices strict ordering per restaurant.
Fix 2: Custom partitioner that detects high-volume keys and spreads them.
Fix 3: Separate high-volume restaurants onto a dedicated high-throughput topic with more partitions.

Load Balancing

Load balancers distribute traffic across multiple servers to maximize availability, throughput, and reliability while minimizing response time.

▲ Load Balancing Algorithms: Round Robin, Least Connections, IP Hash, Weighted — with visual load distribution
AlgorithmHow It WorksBest ForAvoid When
Round RobinCycle through servers in sequenceEqual capacity, stateless servicesLong-lived connections (WebSockets)
Least ConnectionsRoute to server with fewest active connectionsLong-lived conns, variable request timeVery short requests (overhead)
Weighted Round RobinTraffic proportional to server weightMixed capacity, canary deploysWeights need manual tuning
IP Hashhash(client_IP) → always same serverSession affinity without shared stateUsers behind NAT (all → one server)
Least Response TimeLowest latency + fewest connectionsLatency-sensitive APIsHigh monitoring overhead
Consistent HashingHash to ring; servers own rangesCache layers (minimize resharding)Complex operational setup

L4 vs L7 Load Balancer

L4 — Transport Layer (TCP/UDP)

  • Routes by IP + Port only — no content inspection
  • Faster — minimal processing per packet
  • SSL termination: NO (passes through encrypted)
  • Cannot inspect HTTP headers or URL paths
  • Examples: AWS NLB, HAProxy TCP mode
  • Use: DB proxies, game servers, IoT, DNS

L7 — Application Layer (HTTP)

  • Routes by URL path, headers, cookies, body
  • SSL termination: YES — decrypts at load balancer
  • A/B testing, canary deploys by header
  • Content routing: /api → svc-a, /images → svc-b
  • Examples: AWS ALB, NGINX, Envoy, Traefik
  • Use: Microservices, REST APIs, gRPC routing

Failure Scenarios

🔥
Uneven Traffic — Hot Server Problem
Problem: 80% of traffic hitting 2 of 10 servers while others are idle

Solutions

  • Check algorithm: If connections are long-lived, Round Robin creates imbalance. Switch to Least Connections.
  • Sticky sessions: Session affinity can pin too many users to one server. Move to centralized Redis sessions instead.
  • Health check frequency: Tune to 5s intervals to quickly rebalance when a server recovers.
  • Autoscaling: Trigger scale-out when CPU > 70% for 2 min. New servers join the LB pool automatically.
  • Weighted routing: Temporarily lower weight of overloaded server while investigating root cause.
⚡
Stateful Service — Session Not Found
Problem: User logs in on Server A but next request routes to Server B with no session

Solutions

  • Option 1 — Sticky Sessions: LB routes same client to same server via cookie. Risk: uneven load; session lost on crash.
  • Option 2 — Centralized Session Store (BEST): All servers read/write sessions to Redis. Any server handles any request.
  • Option 3 — JWT Tokens (Most Scalable): Stateless auth token carries all user info. No server-side session needed.
  • Design Rule: Services should be stateless. State belongs in Redis or DB, never in-process memory.
🔥
Load Balancer is Single Point of Failure
Problem: The LB itself crashes — all traffic drops

Solutions

  • Active-Passive HA: Secondary LB on hot standby. VIP (Virtual IP) floats via keepalived/VRRP. Failover < 2s.
  • Active-Active: Both LBs handle traffic. DNS round-robins between their IPs. No single point.
  • Cloud LBs (Preferred): AWS ALB/NLB are managed, multi-AZ by default, >99.99% availability. Use unless self-hosting.
  • External Monitoring: Use external health checks (not self-monitoring) on the LB itself. PagerDuty on LB health endpoint.

CDN — Content Delivery Network

CDNs cache content at globally distributed edge nodes (PoPs), serving users from the nearest location — reducing latency from 150ms to under 5ms for static assets.

▲ CDN Architecture: user → nearest PoP → origin (only on miss), cache hit vs miss, and invalidation strategies

What to Cache

✅ Cache on CDN

  • Static assets: JS, CSS, images, fonts (long TTL + hash in filename)
  • Public API responses (non-personalized)
  • Video/audio streaming (HLS segments)
  • Documentation, blog posts, landing pages
  • Product catalog, search results (short TTL)
  • Publicly downloadable PDFs/assets

❌ Never Cache on CDN

  • User-specific data: account info, order history, cart
  • Payment and checkout flows (PCI compliance)
  • Auth tokens, session data, JWTs
  • Real-time data: live scores, stock prices
  • Write operations: POST/PUT/PATCH/DELETE
  • Admin pages, personalized content

Cache-Control Headers

HeaderMeaningExample Scenario
Cache-Control: max-age=31536000Cache for 1 yearJS/CSS with content hash in filename
Cache-Control: no-cacheRevalidate with origin before servingHTML pages that change on every deploy
Cache-Control: no-storeNever cache anywhereAuth responses, payment receipts
Cache-Control: privateBrowser may cache; CDN must notPersonalized user dashboard HTML
Cache-Control: s-maxage=3600CDN caches 1 hour (overrides max-age at CDN)API responses cacheable only at edge
Vary: Accept-EncodingCache separate variants per encodingGzip vs Brotli compressed versions

Scenarios

🔥
Stale Content After Deployment
Problem: Deploy new JS bundle but users still get old version from CDN edge cache for hours

Solutions

  • Cache Busting (Best): Include content hash in filename → app.bundle.a3f9b2c1.js. Hash changes = new URL = CDN gets fresh copy automatically.
  • Versioned Paths: /static/v42/app.js — increment version in deploy pipeline.
  • CDN Purge API: Call Cloudflare/CloudFront purge API as step in CI/CD. Invalidate specific files or /static/* prefix.
  • Short TTL on HTML: HTML (which references hashed asset URLs) set to no-cache or 60s. Always gets latest asset references.
  • Surrogate-Key / Cache-Tag: Tag all 'checkout-v2' assets. Single API call purges all tagged content atomically.
⚡
Low CDN Hit Ratio — Not Improving Latency
Problem: CDN hit rate is 30% — most requests still going to origin, adding latency

Solutions

  • Normalize cache keys: Strip irrelevant query params (?utm_source, ?fbclid) before cache lookup. Same content, different URLs = many misses.
  • Increase TTL: Images/fonts to 1 year with cache busting. API responses to 60s where acceptable.
  • Pre-warm cache: Push popular content to all PoPs before a major event (product launch, sale).
  • Tiered caching: Edge → Regional → Origin. Regional cache hit is still faster than origin, reduces origin load on edge miss.
  • Analyse Vary headers: Overly broad Vary (e.g., Vary: Cookie) creates many cache variants, destroying hit ratio.

Distributed Systems

▲ CAP Theorem: the three-way trade-off, CP vs AP systems, and real-world decision guide
💡 How to Answer 'CP or AP?' in Interviews

Don't recite the theorem — reason from business consequences. Ask: 'What's worse — returning slightly stale data, or returning an error?' Payments/inventory = CP (wrong data is catastrophic). Social feeds/likes = AP (stale for a few seconds is fine). Shopping cart = typically AP (reconcile on checkout). Most modern systems are tunable per operation (Cassandra quorum settings, DynamoDB consistency option).

🔄
Partial Failure — Distributed Transaction Inconsistency
Problem: Order placed, inventory reserved, payment charged — but shipment creation fails. Inconsistent state.

Solutions

  • Saga compensation: Define compensating transaction for each step. Payment fails → emit 'ReleaseInventory' → emit 'CancelOrder'. Each compensation is idempotent.
  • Transactional Outbox: Service writes business data + event in same local DB transaction. Outbox relay publishes to Kafka. Eliminates dual-write.
  • Idempotent consumers: Every service checks if saga_id already processed before acting. Safe to replay on failure.
  • Saga timeout: Each step has a deadline (30s). If 'reserve-inventory' hasn't responded → treat as failure → compensate.
  • State persistence: Save saga state (steps completed, current state) in DB. Can resume after service crash or restart.

Fault Tolerance & Reliability

▲ Circuit Breaker State Machine: CLOSED → OPEN → HALF-OPEN transitions, config values, and implementation
🔥
Cascading Failure — One Slow Service Crashes Everything
Problem: Payment service is slow (5s response). Order service calls it synchronously. Thread pool exhausts. Order service crashes.

Solutions

  • Circuit Breaker: If 50% of calls in 10s window fail/timeout → trip to OPEN. Order service returns fallback immediately.
  • Tight Timeout: Payment service timeout = 1s (not 30s default). Fail fast beats thread exhaustion.
  • Bulkhead: Separate thread pool for payment service calls. Pool exhaustion affects only payment, not all order operations.
  • Fallback: Return 'payment pending' response, queue payment for async retry. Don't block user request.
  • Retry with jitter: On circuit CLOSED again, retry with exponential backoff + jitter to avoid immediately re-tripping.

Retry Strategies

▲ Retry Strategies: fixed delay vs exponential backoff vs jitter — timeline showing why jitter prevents thundering herd
StrategyFormulaProduction Ready?Notes
Fixed DelayRetry every 5s❌ NoAll instances retry simultaneously → thundering herd
Exponential Backoffdelay = base × 2^attempt (cap at 30s)⚠️ PartialBetter spread but all instances still retry at same times
Exp Backoff + Jitterdelay = rand(0, base × 2^attempt)✅ YesRandom spread prevents thundering herd. Always use in distributed systems.
Max RetriesRetry ≤ N times then fail✅ RequiredAfter max retries: DLQ or alert. Never retry infinitely.

Bulkhead Pattern

🛡️ Bulkhead Isolation

Isolate workloads into separate resource pools. Thread pool isolation: separate pools per downstream service — Payment pool full → doesn't block Inventory calls. Connection pool limits: Analytics can't exhaust Order service DB connections. Kubernetes limits: CPU/memory limits per pod. Queue isolation: VIP orders queue (dedicated workers) + standard queue — VIP never waits behind bulk.

Database Scaling

▲ Database Scaling Path: single node → read replicas → caching → sharding → multi-region, with checklist

Sharding Strategies

StrategyHowProsProblem
Range-BasedShard by value range (user_id 1–1M = shard1)Simple queries, range scans efficientHot spots if range uneven
Hash-Basedhash(key) % N shardsEven distributionResharding when N changes — all data moves
Consistent HashingHash to ring; nodes claim rangesMinimal resharding when nodes added/removedComplex implementation
Directory-BasedLookup table maps key → shard IDFlexible logicLookup table = new bottleneck
GeographicShard by region (US users → US shard)Data locality, complianceCross-region queries expensive
⚠️ Cross-Shard Query Problem

SELECT * FROM orders JOIN users — if orders and users are on different shards, SQL JOINs won't work. Solutions: (1) Co-locate related data on same shard (shard both by user_id). (2) Denormalize — include user fields in order record. (3) Application-level join — query each shard and merge in app code (slow). (4) Separate OLAP data warehouse (BigQuery, Redshift) for complex analytics. This is why sharding is a last resort.

Before Sharding — Checklist

✅ Exhaust These Options Before Sharding

(1) Optimize slow queries with EXPLAIN ANALYZE. (2) Add missing indexes (covering indexes, composite indexes). (3) Connection pooling via PgBouncer. (4) Add read replicas for read traffic. (5) Add Redis cache for hot data. (6) Vertical scaling (bigger machine). Only shard if still insufficient. Sharding adds massive operational complexity.

🔥
Double Execution of Scheduled Jobs
Problem: 3 instances of a service all run the daily report cron simultaneously — 3 duplicate reports

Solutions

  • Redis Distributed Lock: Before running, acquire SETNX lock_key TTL. Only one instance acquires it; others detect lock and skip.
  • Leader Election: Use Zookeeper/etcd. Only the current leader runs scheduled jobs. Followers stand by and re-elect on failure.
  • DB Lock: INSERT INTO job_locks (job_name, run_date) with UNIQUE constraint. One INSERT succeeds; others get constraint violation → skip.
  • Idempotent Jobs: Even if run twice, check 'has this job run for period X?' before doing work. Store run record in DB.
  • Platform Solution: Kubernetes CronJob guarantees single execution. Temporal handles distributed scheduling natively.
⚡
Delayed Notification Not Firing
Problem: 'Order delivered — rate us!' push should fire 30min after delivery but some don't trigger

Solutions

  • SQS Delay Queue: Publish message with DelaySeconds=1800. SQS holds it and delivers at correct time. Fully managed.
  • Redis Sorted Set: ZADD delayed_jobs (now+delay) job_id. Worker polls ZRANGEBYSCORE 0 now every 5s. Fast O(log N) lookup.
  • DB Polling: SELECT * WHERE execute_at <= NOW() AND status='pending' every 5s. Simple but adds polling overhead.
  • Monitor Drift: Alert if executed_at vs scheduled_at drift exceeds 60s — indicates worker falling behind.

Interview Cheat Sheet

▲ RESHADED: 8-step interview framework with key questions and deliverables for each phase

Problem → Solution Quick Reference

❓ System is slow
Answer: Cache (Redis), CDN, DB indexes, async queues, read replicas
Improve: Profile with traces → find bottleneck → targeted fix
❓ Crashes under load
Answer: Horizontal scaling + LB, autoscaling, rate limiting, circuit breaker
Improve: Load test to find limits; bulkhead isolation
❓ Data inconsistent
Answer: Saga + compensation, idempotency, distributed locks, CDC

Answer: Kafka acks=all, DLQ, consumer lag monitoring, at-least-once + idempotency

❓ Notifications not delivered

⭐ Final Interview Tips

1. Ask clarifying questions first — scale, latency SLO, consistency requirements. Shows structured thinking.
2. Draw the diagram first, then explain — interviewers follow visual flow better than descriptions.
3. Lead with simple design, then evolve: 'This works at 1k QPS; here's how we scale to 100k QPS.'
4. Always discuss trade-offs — every decision has costs. Showing you know them = senior-level thinking.
5. Name real tools (Redis, Kafka, Postgres, Envoy) and explain why you chose each, not just that you know them.
