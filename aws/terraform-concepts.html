Terraform: How it Actually Works

The mental model, lifecycle, providers, state, and real setups — Spring Boot, Python, domain, WAF, Workload Identity.

14 Chapters GCP & AWS Spring Boot + Python Workload Identity

CHAPTER 1 — THE MENTAL MODEL (Read This First)

What Terraform Actually Is

Most people learn Terraform by copying commands. This guide teaches you to understand it — so when something breaks at 2am, you know exactly why.

Terraform is a desired-state engine. You describe what you want to exist. Terraform figures out how to make it exist, and in what order. You never write steps like "first create the VPC, then create the subnet" — you just declare both, and Terraform builds the dependency graph automatically.

This is the single most important idea. Everything else flows from it.

You write:  WHAT you want
Terraform:  figures out HOW and in WHAT ORDER
Cloud APIs: actually create the resources

Compare this to how you'd do it manually:

Manual:  aws ec2 create-vpc → get VPC id → aws ec2 create-subnet --vpc-id <that id> → ...
         (you track state, you handle order, you handle failures)

Terraform: write vpc + subnet declarations → terraform apply
           (Terraform tracks state, handles order, handles idempotency)

The Three Worlds Terraform Juggles

At all times, Terraform is aware of three separate realities:

┌─────────────────────────────────────────────────────────────────────┐
│ WORLD 1: Your .tf files                                             │
│   What you DECLARED you want to exist right now                     │
│   Lives in: your git repo                                           │
├─────────────────────────────────────────────────────────────────────┤
│ WORLD 2: terraform.tfstate                                          │
│   What Terraform LAST CREATED/KNEW ABOUT                           │
│   Lives in: S3 bucket / GCS bucket (production) or local file      │
├─────────────────────────────────────────────────────────────────────┤
│ WORLD 3: The actual cloud (AWS/GCP APIs)                            │
│   What ACTUALLY EXISTS RIGHT NOW                                    │
│   Lives in: the cloud provider                                      │
└─────────────────────────────────────────────────────────────────────┘

terraform plan = diff(World 1, World 3) using World 2 as a cache terraform apply = make World 3 match World 1, then update World 2

This is why: - Deleting something from your .tf files makes Terraform destroy it (World 1 no longer contains it) - Manually changing something in the cloud causes drift (World 2 ≠ World 3) - The state file is precious — it's Terraform's memory of what it created

CHAPTER 2 — WHAT HAPPENS WHEN YOU RUN TERRAFORM

Step 1: terraform init

terraform init

What actually happens, in order:

1. Terraform reads your .tf files looking for:
   - terraform { required_providers { ... } }
   - terraform { backend { ... } }

2. Downloads provider plugins into .terraform/providers/
   Each provider is a separate binary (e.g., terraform-provider-aws)
   These plugins translate your HCL into API calls

3. Initialises the backend
   - If S3/GCS: connects and verifies bucket exists
   - Downloads existing state from remote backend

4. Creates .terraform.lock.hcl
   Records exact provider versions + hashes (like package-lock.json)

The provider is a translator. When you write:

resource "aws_s3_bucket" "my_bucket" {
  bucket = "my-unique-name"
}

The aws provider plugin translates this into:

POST https://s3.amazonaws.com/
Body: CreateBucket(Bucket=my-unique-name, ...)

You never write API calls. The provider handles every API detail.

Step 2: terraform plan

terraform plan

What actually happens:

1. Load all .tf files → build the resource graph in memory

2. Read current state from state file (World 2)

3. For each resource in your config:
   - Call provider's READ operation (refresh from real cloud = World 3)
   - Compare: desired (World 1) vs actual (World 3)

4. Build a list of changes:
   + create   = in World 1, NOT in World 2/3
   - destroy  = NOT in World 1, IS in World 2/3
   ~ update   = in both, but attributes differ (in-place change possible)
  -/+ replace = in both, but a changed attribute forces destroy+recreate

5. Topologically sort the changes (parents before children)

6. Print the plan — but change NOTHING

The plan is a contract. Reading it carefully is not optional — it's your only chance to catch mistakes before they happen. Specifically watch for -/+ (replace) on databases and stateful resources.

Step 3: terraform apply

terraform apply

What actually happens:

1. Acquire state lock (prevents concurrent applies from corrupting state)
   - S3: writes a .tflock file
   - GCS: uses object generation conditions

2. Show the plan again and ask for confirmation (unless -auto-approve)

3. Execute the plan in dependency order:
   For each resource:
     a. Call provider's CREATE/UPDATE/DELETE API
     b. Wait for the operation to complete (some take minutes)
     c. Provider calls READ again to get the final resource attributes
        (like the auto-assigned public IP, the generated ARN, etc.)
     d. Write those attributes to state immediately
        (even if the next resource fails, this one is recorded)

4. Release state lock

5. Write updated state file

Why attributes are written immediately (step 3d): if apply fails halfway through, Terraform knows what was created and what wasn't. On the next apply, it only creates the missing pieces.

Step 4: terraform destroy

terraform destroy

Same as apply, but the "desired state" is empty. Every resource in state gets destroyed, in reverse dependency order (children before parents). You can't destroy a VPC while subnets still exist — Terraform handles the order.

The Refresh

When you run plan or apply, Terraform calls each provider's READ for every resource in state. This is called a refresh. It's how Terraform detects: - Resources deleted manually in the console (they disappear from World 3) - Attributes changed manually (drift) - Resources that still exist (no change needed)

You can skip the refresh with -refresh=false for speed, but then Terraform is working from stale data.

CHAPTER 3 — STATE: THE MOST IMPORTANT THING TO UNDERSTAND

What State Actually Contains

Open a terraform.tfstate file and you'll see JSON like this:

{
  "version": 4,
  "terraform_version": "1.6.0",
  "resources": [
    {
      "type": "aws_s3_bucket",
      "name": "my_bucket",
      "provider": "provider[\"registry.terraform.io/hashicorp/aws\"]",
      "instances": [
        {
          "schema_version": 0,
          "attributes": {
            "id": "my-unique-name",
            "arn": "arn:aws:s3:::my-unique-name",
            "bucket": "my-unique-name",
            "region": "us-east-1",
            "tags": { "Environment": "dev" }
          }
        }
      ]
    }
  ]
}

State stores every attribute of every resource Terraform created. This includes: - The resource's unique ID (how Terraform finds it on refresh) - Auto-generated values (ARNs, IPs, generated passwords) - All configuration values

This is why state contains secrets. If you create a database with a password, that password is in the state file in plaintext. Always encrypt your remote state.

Why You Never Edit State By Hand

The state file has a serial number. If you edit it by hand and get the JSON wrong, or the serial doesn't match, Terraform can't read it. Use terraform state commands instead:

terraform state list                    # list all resources in state
terraform state show aws_s3_bucket.x   # show one resource's state
terraform state mv old.name new.name   # rename without destroying
terraform state rm aws_s3_bucket.x     # remove from state (doesn't destroy the real resource)
terraform import aws_s3_bucket.x name  # bring an existing resource INTO state

Remote State: Why and How

Local state (terraform.tfstate on your laptop) is fine for solo experiments. In teams:

Problem 1: Two people run apply simultaneously → state corruption
Problem 2: Your laptop dies → state is gone → Terraform doesn't know what exists
Problem 3: State contains secrets → shouldn't be in git
Problem 4: Nobody else can run Terraform → blocked on one machine

Remote state solves all four:

# AWS: state in S3 with native locking
terraform {
  backend "s3" {
    bucket       = "my-terraform-state"
    key          = "prod/webapp/terraform.tfstate"   # path within bucket
    region       = "us-east-1"
    encrypt      = true                               # AES-256 or KMS
    use_lockfile = true                               # prevents concurrent applies
  }
}

# GCP: state in GCS (locking is automatic)
terraform {
  backend "gcs" {
    bucket = "my-terraform-state"
    prefix = "prod/webapp"
  }
}

The key is like a folder path. Different projects use different keys so their state doesn't collide. A common pattern:

team/environment/component/terraform.tfstate
platform/prod/networking/terraform.tfstate
platform/prod/database/terraform.tfstate
payments/dev/app/terraform.tfstate

Separate state = separate blast radius. A broken apply in payments/dev can't affect platform/prod.

State Locking in Detail

When you run apply: 1. Terraform writes a lock record to the backend (S3: a .tflock file; GCS: a lock object) 2. The lock contains: who locked it, when, what operation 3. If another apply tries to start: it reads the lock and fails with: Error: Error acquiring the state lock Lock Info: ID=abc123, Operation=apply, Who=alice@machine, Created=... 4. When apply finishes (success or failure): lock is released

If Terraform crashes mid-apply, the lock stays. Use terraform force-unlock <lock-id> — but only when you're 100% sure no apply is running.

CHAPTER 4 — PROVIDERS: THE PLUGINS THAT DO THE WORK

How Providers Work Internally

A provider is a Go binary that implements a protocol. It has four operations per resource type:

CREATE  → call the cloud API to create the resource, return all attributes
READ    → call the cloud API to check if the resource still exists + get current state
UPDATE  → call the cloud API to change attributes that can be changed in-place
DELETE  → call the cloud API to destroy the resource

When you write:

resource "google_compute_instance" "web" {
  name         = "my-vm"
  machine_type = "e2-micro"
  ...
}

Terraform calls the google provider binary, which calls:

POST https://compute.googleapis.com/compute/v1/projects/{project}/zones/{zone}/instances
Authorization: Bearer <your gcloud credentials>
Body: { name: "my-vm", machineType: "zones/.../machineTypes/e2-micro", ... }

You are just writing a nice language on top of REST API calls.

Provider Authentication

Providers need credentials to call APIs. They find them in this order:

AWS provider:

1. environment variables: AWS_ACCESS_KEY_ID + AWS_SECRET_ACCESS_KEY
2. ~/.aws/credentials file (what `aws configure` creates)
3. IAM instance role (if running ON an EC2 instance)
4. ECS task role / Lambda execution role
5. Web Identity Token (OIDC — for CI/CD, the modern way)

Google provider:

1. GOOGLE_CREDENTIALS env var (path to a service account JSON key)
2. Application Default Credentials (ADC)
   - gcloud auth application-default login sets this up
   - Workload Identity sets this up automatically on GKE
3. Metadata server (if running ON a GCE instance or GKE pod)

The important lesson: In CI/CD, never store credentials as secrets in CI. Use OIDC/Workload Identity so CI gets temporary credentials by proving its identity. More on this in the setup chapters.

Provider Version Constraints

terraform {
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 5.0"      # >= 5.0.0, < 6.0.0
    }
    google = {
      source  = "hashicorp/google"
      version = ">= 5.0, < 6.0"
    }
  }
}

Version constraint operators:

= 5.1.0    exactly 5.1.0
!= 5.1.0   anything except 5.1.0
>= 5.0     5.0 or higher
~> 5.0     >= 5.0, < 6.0 (the patch/minor are free, major is locked)
~> 5.1     >= 5.1, < 6.0 (same)

Always pin to ~> MAJOR.MINOR in production. Provider major versions often contain breaking changes. Unpinned = your infra might change behaviour after a teammate's init.

CHAPTER 5 — HCL DEEPLY UNDERSTOOD

Resources vs Data Sources: The Core Distinction

# RESOURCE: Terraform CREATES and MANAGES this
resource "aws_vpc" "main" {
  cidr_block = "10.0.0.0/16"
}
# Terraform calls: CREATE vpc, UPDATE vpc, DELETE vpc

# DATA SOURCE: Terraform READS this but does NOT manage it
data "aws_ami" "amazon_linux" {
  most_recent = true
  owners      = ["amazon"]
  filter {
    name   = "name"
    values = ["al2023-ami-*-x86_64"]
  }
}
# Terraform calls: READ only. Never creates or destroys.

Data sources are how you reference things Terraform didn't create: - The latest AMI id (changes every few weeks as Amazon patches) - An existing VPC you're not managing in this config - Your AWS account id - Available availability zones

How Terraform Resolves References

resource "aws_vpc" "main" {
  cidr_block = "10.0.0.0/16"
}

resource "aws_subnet" "web" {
  vpc_id     = aws_vpc.main.id        # reference to the vpc's id attribute
  cidr_block = "10.0.1.0/24"
}

When Terraform sees aws_vpc.main.id, it knows: 1. aws_subnet.web depends on aws_vpc.main 2. Create the VPC first, get its id from the API response 3. Use that id when creating the subnet

You never need to write the VPC id anywhere. You reference it by the Terraform address of the resource. Terraform figures out the ordering from the reference graph.

The dependency graph in action:

aws_vpc.main
    └── aws_subnet.web
            └── aws_instance.app
                    └── aws_eip.app

Apply: vpc → subnet → instance → eip Destroy: eip → instance → subnet → vpc (reverse)

The Lifecycle Meta-Argument: What Happens During Apply

Every resource has a hidden lifecycle block with defaults you can override:

resource "aws_db_instance" "main" {
  # ...
  lifecycle {
    # 1. create_before_destroy (default: false)
    # If a replacement is needed (a new DB), create the new one FIRST,
    # then destroy the old one. Reduces downtime on replacements.
    create_before_destroy = true

    # 2. prevent_destroy (default: false)
    # terraform destroy or a plan that would destroy this resource
    # returns an error. Your safety net for production databases.
    prevent_destroy = true

    # 3. ignore_changes (default: [])
    # Terraform won't treat external changes to these attributes as drift.
    # Use when something outside Terraform manages these (e.g., autoscaler)
    ignore_changes = [
      allocated_storage,   # RDS can autoscale storage; we don't want to fight it
      tags["LastModified"] # some tools auto-update this tag
    ]

    # 4. replace_triggered_by (default: [])
    # Force replacement of THIS resource when another changes.
    # E.g., replace the launch template when the AMI changes.
    replace_triggered_by = [aws_ami.app]
  }
}

When does a resource get REPLACED (not updated)?

Some attributes are immutable — the cloud API doesn't let you change them on an existing resource. If you change one, Terraform must destroy the old resource and create a new one. Examples: - S3 bucket name (changing it = new bucket) - RDS engine version (major) = new instance - AZ of a subnet = new subnet - EC2 instance type (some require replacement, some don't)

The plan shows this as -/+. Always look for it.

Meta-Arguments Every Resource Has

resource "aws_instance" "app" {
  # ...

  # count: create N copies; indexed as aws_instance.app[0], [1], etc.
  count = 3

  # for_each: create one per map entry or set member
  for_each = toset(["us-east-1a", "us-east-1b"])
  availability_zone = each.value  # or each.key for maps

  # depends_on: explicit dependency (rarely needed — use references instead)
  depends_on = [aws_iam_role_policy_attachment.app]

  # provider: use a specific provider alias (for multi-region)
  provider = aws.us-west-2

  lifecycle { ... }
}

count vs for_each — the crucial difference:

# count uses POSITION as the key
resource "aws_iam_user" "dev" {
  count = 3
  name  = "dev-${count.index}"
}
# Users: dev-0, dev-1, dev-2
# Addresses: aws_iam_user.dev[0], [1], [2]
# If you REMOVE dev-1: dev-2 becomes [1], gets DESTROYED AND RECREATED

# for_each uses NAME as the key
resource "aws_iam_user" "dev" {
  for_each = toset(["alice", "bob", "carol"])
  name     = each.key
}
# Users: alice, bob, carol
# Addresses: aws_iam_user.dev["alice"], ["bob"], ["carol"]
# If you REMOVE bob: only bob is destroyed; alice and carol untouched

Rule: Use for_each for any collection where members might be added or removed. Use count only as a 0/1 toggle (conditional resource).

CHAPTER 6 — MODULES: HOW TEAMS SCALE TERRAFORM

What a Module Is (Really)

Every directory of .tf files is a module. When you run terraform apply in a directory, you're running the root module. You call other directories as child modules:

module "vpc" {
  source = "./modules/vpc"       # local path
  # OR
  source = "git::https://github.com/org/tf-modules.git//vpc?ref=v1.2.0"
  # OR
  source = "terraform-aws-modules/vpc/aws"  # Terraform Registry
  version = "~> 5.0"

  # inputs = the module's variables
  cidr     = "10.0.0.0/16"
  azs      = ["us-east-1a", "us-east-1b"]
}

# outputs from child modules are accessed as:
resource "aws_instance" "app" {
  subnet_id = module.vpc.private_subnet_ids[0]
  #           ^^^^^^^^                      ^^^
  #           module name                   output name
}

How Data Flows Through Modules

Root module
├── variables.tf    ← inputs FROM the caller (terraform.tfvars or -var flags)
├── main.tf         ← resources + calls to child modules
├── outputs.tf      ← outputs TO the caller (if this is itself a child)
│
└── modules/
    └── vpc/
        ├── variables.tf    ← what the root module passes in
        ├── main.tf         ← the actual VPC/subnet resources
        └── outputs.tf      ← vpc_id, subnet_ids etc. for the root to use

Data only flows through explicit interfaces. A child module cannot reach into its parent's state. A parent cannot see inside a child except through outputs. This is the encapsulation that makes modules composable.

Module Versions and Why They Matter

module "eks" {
  source  = "terraform-aws-modules/eks/aws"
  version = "~> 20.0"   # This is pinned
}

Without version pinning, terraform init downloads the latest version every time. If the module's author makes a breaking change, your next plan might want to destroy and recreate your production cluster.

When consuming a published module version, always: 1. Read its CHANGELOG before bumping versions 2. Test the new version in dev/staging first 3. Bump prod separately with a manual review

CHAPTER 7 — THE COMPLETE TERRAFORM WORKFLOW FOR REAL ORGS

The Standard Git-Based Flow

Developer changes .tf files
         │
         ▼
   git commit + push
         │
         ▼
   CI pipeline (on PR):
   ┌────────────────────┐
   │ terraform fmt -check│ ← fails if formatting wrong
   │ terraform validate  │ ← checks syntax + internal consistency
   │ tflint              │ ← provider-specific lint (bad instance types, deprecated args)
   │ tfsec / trivy       │ ← security issues (open SGs, unencrypted disks)
   │ terraform plan      │ ← the actual planned changes
   │ post plan to PR     │ ← reviewer reads the plan
   └────────────────────┘
         │
         ▼
   Human reviews the PLAN (not just the code)
         │
         ▼
   Merge to main
         │
         ▼
   CI pipeline (on merge):
   terraform apply ← with manual approval gate for prod

The plan comment on the PR is the key review artifact. Reviewing the HCL is good. Reviewing the plan is essential. The plan is the contract of what will actually change.

Environment Separation

terraform/
├── modules/          ← shared modules (no state here)
│   ├── vpc/
│   ├── eks/
│   └── database/
└── environments/
    ├── dev/
    │   ├── backend.tf      ← key: "dev/terraform.tfstate"
    │   ├── main.tf         ← calls modules with dev settings
    │   └── terraform.tfvars
    ├── staging/
    │   ├── backend.tf      ← key: "staging/terraform.tfstate"  ← DIFFERENT STATE
    │   └── ...
    └── prod/
        ├── backend.tf      ← key: "prod/terraform.tfstate"    ← DIFFERENT STATE
        └── ...

Separate state files per environment is the critical property. If your dev apply corrupts state, it cannot affect prod state. They are independent files in separate paths in the same bucket, or even separate buckets.

CHAPTER 8 — REAL EXAMPLE: Spring Boot Application on GKE

Let's build this completely. A Spring Boot app, containerised, running on GKE, with a Cloud SQL database, domain name, Cloud Armor WAF, and Workload Identity (no service account keys anywhere).

What We're Building

Internet
   │
   ▼
Cloud Armor WAF (security layer)
   │
   ▼
Global HTTPS Load Balancer (your domain: app.company.com)
   │
   ▼
GKE Cluster (private nodes)
   │ Workload Identity (no keys)
   ▼
Cloud SQL (PostgreSQL, private IP)

Step 1: Project and APIs

# terraform/gcp/project/main.tf
# Enable all the APIs we need (GCP requires explicit enablement)
locals {
  project = "my-company-prod"
  region  = "us-central1"
}

resource "google_project_service" "apis" {
  for_each = toset([
    "container.googleapis.com",         # GKE
    "sqladmin.googleapis.com",          # Cloud SQL
    "servicenetworking.googleapis.com", # private service access (SQL private IP)
    "secretmanager.googleapis.com",     # secrets
    "cloudarmor.googleapis.com",        # Cloud Armor WAF
    "dns.googleapis.com",               # Cloud DNS
    "compute.googleapis.com",           # VPC, load balancer
    "iam.googleapis.com",               # IAM + Workload Identity
  ])
  project = local.project
  service = each.value
  disable_on_destroy = false  # don't disable API when you destroy this resource
}

Why disable_on_destroy = false? If you accidentally destroy this resource, you don't want all your APIs turned off. This is a safe default.

Step 2: VPC (Private Cluster Foundation)

# terraform/gcp/networking/main.tf

resource "google_compute_network" "main" {
  name                    = "main-vpc"
  auto_create_subnetworks = false  # we create subnets explicitly
  project                 = local.project
}

resource "google_compute_subnetwork" "gke" {
  name          = "gke-subnet"
  ip_cidr_range = "10.10.0.0/20"    # 4096 IPs for nodes
  region        = local.region
  network       = google_compute_network.main.id
  project       = local.project

  # GKE needs secondary ranges for Pods and Services
  # (pods get IPs from a separate range, not the node range)
  secondary_ip_range {
    range_name    = "pods"
    ip_cidr_range = "10.20.0.0/16"   # 65536 pod IPs
  }
  secondary_ip_range {
    range_name    = "services"
    ip_cidr_range = "10.30.0.0/20"   # 4096 service IPs
  }

  private_ip_google_access = true  # nodes can reach Google APIs without external IPs
}

# Cloud NAT: lets private nodes reach the internet (for pulling images, apt-get etc.)
# WITHOUT having public IPs themselves
resource "google_compute_router" "main" {
  name    = "main-router"
  region  = local.region
  network = google_compute_network.main.id
  project = local.project
}

resource "google_compute_router_nat" "main" {
  name                               = "main-nat"
  router                             = google_compute_router.main.name
  region                             = local.region
  project                            = local.project
  nat_ip_allocate_option             = "AUTO_ONLY"      # GCP manages the NAT IPs
  source_subnetwork_ip_ranges_to_nat = "ALL_SUBNETWORKS_ALL_IP_RANGES"
}

# Private Service Access: lets Cloud SQL get a private IP in OUR VPC

Step 4: Workload Identity — The Most Important Security Concept

Workload Identity lets a Kubernetes pod act as a Google Cloud service account WITHOUT any service account key files. This is the secure way to give pods access to GCP APIs.

Traditional (BAD):
  Pod → reads /var/secrets/key.json (mounted secret) → calls GCP API
  Problem: the key file can be stolen, expires, needs rotation

Workload Identity (GOOD):
  Pod → calls metadata server → GCP verifies "this pod has k8s SA 'myapp'"
      → GCP checks IAM binding: "k8s SA 'myapp' = GCP SA 'myapp-gcp'"
      → returns short-lived token for 'myapp-gcp' → calls GCP API
  No key files. Token is auto-rotated every hour.

        interval_sec = 60
      }

    action   = "allow"
    priority = 2147483647  # max int32 = the default rule

# terraform/aws/irsa/main.tf

  source  = "terraform-aws-modules/iam/aws//modules/iam-role-for-service-accounts-eks"
  version = "~> 5.0"

  role_name = "python-app"

  oidc_providers = {
    main = {
      provider_arn               = module.eks.oidc_provider_arn

      #                             namespace  k8s SA name
    }
  }

  # Step 2: Attach policies defining what the app can DO
  role_policy_arns = {
    secrets_access = aws_iam_policy.python_app_secrets.arn
    s3_access      = aws_iam_policy.python_app_s3.arn
  }
}

resource "aws_iam_policy" "python_app_secrets" {
  name = "python-app-secrets"
  policy = jsonencode({
    Version = "2012-10-17"
    Statement = [{
      Effect   = "Allow"
      Action   = ["secretsmanager:GetSecretValue"]
      Resource = [
        aws_secretsmanager_secret.db_password.arn,
        aws_secretsmanager_secret.api_keys.arn,
      ]
      # Note: specific ARNs, NOT "arn:aws:secretsmanager:*:*:secret:*"
      # Least privilege: only these exact secrets
    }]

}

  name = "python-app-s3"
  policy = jsonencode({
    Version = "2012-10-17"
    Statement = [{
      Effect = "Allow"
      Action = ["s3:GetObject", "s3:PutObject"]
      Resource = "${aws_s3_bucket.app_data.arn}/*"
    }]
  })
}

# The OIDC mechanism explained:
# 1. EKS creates an OIDC provider (a URL like https://oidc.eks.us-east-1.amazonaws.com/id/...)
# 2. When a pod starts, the kubelet mounts a JWT token signed by that OIDC provider
# 3. The pod's AWS SDK sees this token and calls STS AssumeRoleWithWebIdentity
# 4. STS verifies the token with the OIDC provider
# 5. STS checks the role's trust policy: "does namespace:service-account match?"
# 6. If yes, returns temporary AWS credentials (valid 1 hour, auto-renewed)
# 7. Pod uses those credentials for all AWS API calls
# Result: no access keys, no secrets to rotate, no IAM users

In Kubernetes (GitOps repo):

apiVersion: v1

  name: python-app
  namespace: production

    # This annotation is what triggers IRSA
    eks.amazonaws.com/role-arn: arn:aws:iam::123456789012:role/python-app

  skip_final_snapshot       = false
  final_snapshot_identifier = "prod-app-db-final-${formatdate("YYYY-MM-DD", timestamp())}"

  # Performance Insights: shows you WHICH queries are slow
  performance_insights_enabled          = true
  performance_insights_retention_period = 7

  lifecycle {
    prevent_destroy = true
    ignore_changes  = [password]  # allow external rotation without drift
  }
}

resource "aws_security_group" "rds" {
  name   = "rds-sg"
  vpc_id = module.vpc.vpc_id

  ingress {
    from_port       = 5432
    to_port         = 5432
    protocol        = "tcp"
    security_groups = [module.eks.node_security_group_id]  # ONLY from EKS nodes
    description     = "PostgreSQL from EKS nodes"
  }
  # NO outbound rules = default deny all outbound from the DB
}

Why ignore_changes = [password]: once the DB is created with an initial password, you'll likely set up automatic rotation via Secrets Manager rotation Lambda. That Lambda will change the password in both RDS and Secrets Manager. Without ignore_changes, Terraform would see the password in state differs from reality and try to change it back on the next apply.

CHAPTER 10 — WHAT EXACTLY HAPPENS WHEN TERRAFORM TOUCHES A KUBERNETES CLUSTER

The Challenge

Terraform can provision a GKE/EKS cluster. But what about deploying apps TO that cluster? Terraform has a kubernetes provider that can create Deployments, Services, etc. But you generally shouldn't use it for app deployments. Here's why.

Terraform's kubernetes Provider: Appropriate vs Inappropriate Uses

APPROPRIATE (cluster-level, bootstrap):
  ✓ Creating namespaces
  ✓ Installing Argo CD via helm_release
  ✓ Creating the root application for App-of-Apps
  ✓ ClusterRoles that need to exist before anything else
  ✓ StorageClasses

INAPPROPRIATE (application-level):
  ✗ Deploying your app's Deployment/Service/Ingress
  ✗ Managing ConfigMaps that apps update
  ✗ Anything that changes frequently

Why not Terraform for apps?

  1. Slow: Terraform plan re-reads every k8s resource it manages. 100 resources = 100 API calls on every plan, even if nothing changed.

  2. No continuous reconciliation: Terraform only reconciles when you run it. If someone kubectl edits a deployment, that drift persists until the next apply.

  3. No health awareness: Terraform applies the manifest and considers it done. It doesn't know if the Deployment's pods are actually running or crashing. Argo CD does — it has health checks for every resource type.

  4. Coupling: app changes require a Terraform pipeline run, not a git commit to the app config.

The Right Split

TERRAFORM DOES:
  terraform apply
    ├── Creates GKE/EKS cluster
    ├── Creates node pools
    ├── Creates IAM/Workload Identity
    └── helm_release "argocd" { ... }   ← installs Argo CD

ARGO CD DOES (from git):
  ├── Installs cluster add-ons (ingress, cert-manager, etc.)
  ├── Deploys all your applications
  └── Continuously reconciles everything

What helm_release Actually Does

resource "helm_release" "argocd" {
  name             = "argocd"
  repository       = "https://argoproj.github.io/argo-helm"
  chart            = "argo-cd"
  version          = "7.7.0"
  namespace        = "argocd"
  create_namespace = true

  set {
    name  = "server.service.type"
    value = "LoadBalancer"
  }

  values = [yamlencode({
    configs = {
      params = {
        "server.insecure" = false
      }
    }
  })]

  wait          = true    # wait until all pods are running before Terraform considers it done
  wait_for_jobs = true    # wait for Helm hooks (Jobs) to complete
  timeout       = 300     # seconds

  lifecycle {
    ignore_changes = [metadata]  # Helm adds metadata that changes on each deploy
  }
}

What helm_release does under the hood:

1. Downloads the Helm chart (tarball)
2. Renders it with the provided values → list of Kubernetes manifests
3. Applies those manifests to the cluster (like kubectl apply)
4. Stores the rendered manifests in a Kubernetes Secret (Helm's own state)
5. If wait=true: watches the manifests until all Pods are Running/Ready
6. Stores the release info in Terraform state

CHAPTER 11 — COMMON REAL-WORLD PATTERNS

Pattern 1: Secrets That the App Needs at Runtime

Wrong way (common beginner mistake):

resource "aws_ecs_task_definition" "app" {
  container_definitions = jsonencode([{
    environment = [
      { name = "DB_PASSWORD", value = var.db_password }  # in state, in logs, in code
    ]
  }])
}

Right way:

# Store in Secrets Manager
resource "aws_secretsmanager_secret_version" "db" {
  secret_id     = aws_secretsmanager_secret.db.id
  secret_string = jsonencode({ password = random_password.db.result })
}

# Reference it by ARN in the task definition
resource "aws_ecs_task_definition" "app" {
  container_definitions = jsonencode([{
    secrets = [{
      name      = "DB_PASSWORD"
      valueFrom = "${aws_secretsmanager_secret.db.arn}:password::"
      # ECS fetches this at task start, injects as env var, never logs it
    }]
  }])
}

On EKS: use the AWS Secrets Manager CSI driver (mounts secrets as files) or External Secrets Operator (creates k8s Secrets from SM). On GKE: use External Secrets Operator with Secret Manager backend.

Pattern 2: Multiple AWS Regions / GCP Regions

# Provider aliases for multi-region
provider "aws" {
  alias  = "us_east"
  region = "us-east-1"
}

provider "aws" {
  alias  = "eu_west"
  region = "eu-west-1"
}

# Deploy the same module to two regions
module "us" {
  source    = "./modules/webapp"
  providers = { aws = aws.us_east }
  env       = "prod-us"
}

module "eu" {
  source    = "./modules/webapp"
  providers = { aws = aws.eu_west }
  env       = "prod-eu"
}

Pattern 3: Conditional Resources (Feature Flags in HCL)

variable "enable_waf" {
  type    = bool
  default = true
}

variable "environment" {
  type    = string
}

# WAF only in production
resource "aws_wafv2_web_acl" "main" {
  count = var.environment == "prod" && var.enable_waf ? 1 : 0
  # ...
}

# Reference it safely
resource "aws_alb" "main" {
  # ...
}

resource "aws_wafv2_web_acl_association" "main" {
  count        = var.environment == "prod" && var.enable_waf ? 1 : 0
  resource_arn = aws_alb.main.arn
  web_acl_arn  = aws_wafv2_web_acl.main[0].arn
}

Pattern 4: terraform_remote_state (Cross-Stack References)

When your networking is in one state file and your app is in another:

# In environments/prod/app/main.tf
# Read outputs from the networking stack
data "terraform_remote_state" "networking" {
  backend = "s3"
  config = {
    bucket = "my-terraform-state"
    key    = "prod/networking/terraform.tfstate"
    region = "us-east-1"
  }
}

# Use those outputs
resource "aws_instance" "app" {
  subnet_id = data.terraform_remote_state.networking.outputs.private_subnet_ids[0]
  vpc_security_group_ids = [data.terraform_remote_state.networking.outputs.app_sg_id]
}

Alternative (often better): use SSM Parameter Store or GCP Secret Manager to publish outputs. The networking stack writes values there; the app stack reads them. Looser coupling — you can change one without the other re-reading state.

CHAPTER 12 — TERRAFORM IMPORT: BRINGING EXISTING RESOURCES UNDER MANAGEMENT

The Scenario

Someone created an S3 bucket by hand. You want Terraform to manage it now without destroying and recreating it.

# Step 1: Write the resource block in your .tf file first
# (Terraform needs the resource definition before it can import)

# Step 2: Import the existing resource into state
terraform import aws_s3_bucket.legacy my-existing-bucket-name

# Step 3: Run plan — Terraform will show differences between
# your .tf file and what's actually configured.
# Edit your .tf file to match (or configure the resource to match your .tf)
terraform plan

# Step 4: Apply to reconcile any differences
terraform apply

Import blocks (modern way, TF 1.5+):

import {
  to = aws_s3_bucket.legacy
  id = "my-existing-bucket-name"
}

resource "aws_s3_bucket" "legacy" {
  bucket = "my-existing-bucket-name"
  # ... Terraform can now generate this block automatically
}

terraform plan -generate-config-out=generated.tf
# Terraform writes the resource block by reading the real resource
# You review generated.tf, clean it up, copy it to your main .tf

terraform import does NOT: - Modify the real resource - Know what your .tf file says - Validate that your .tf matches reality (that's what plan is for)

Useful Debug Flags

# See the full plan details in JSON
terraform plan -out=plan.bin
terraform show -json plan.bin | jq '.resource_changes[] | select(.change.actions | contains(["delete"]))'

CHAPTER 14 — THE COMPLETE CHECKLIST

Before You Write Any HCL

  • Do I have a state bucket? Is it versioned + encrypted?
  • Are my provider credentials set? (aws sts get-caller-identity or gcloud auth list)
  • Do I have budget alerts set on this account?
  • Do I know what environment this is? (dev/staging/prod)
  • Is the state key unique to this project+environment?

Before Every apply

  • Did I read the entire plan output?
  • Are there any -/+ (replace) operations? Do I understand what causes them?
  • Are there any destroy operations I didn't expect?
  • If this is prod: is there a second pair of eyes on the plan?
  • Do the outputs make sense?

Before Merging Terraform Code

  • terraform fmt passes?
  • terraform validate passes?
  • Does the PR include the plan output so the reviewer can see what changes?
  • Are resources that shouldn't be destroyed protected with prevent_destroy?
  • Are secrets handled properly (not in code, not in unencrypted state)?
  • Are all resources tagged with at least Owner + Environment?

The Destroy Discipline (For Sandboxes)

At the end of every learning session:

terraform destroy    # type 'yes' when prompted
# Verify in the cloud console that nothing is running

A single forgotten NAT gateway costs ~$32/month. A GPU instance left running overnight can cost hundreds. Treat destroy as part of every learning exercise.

The pattern behind every piece of Terraform is simple: declare what you want, let Terraform figure out how. The complexity you feel early on is the cloud's complexity — Terraform is just making it legible, versionable, and repeatable. Every concept in this guide flows from the three-world model in Chapter 1. When something confuses you, go back there.
